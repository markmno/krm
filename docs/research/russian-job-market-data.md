> Синтезировано из 4 параллельных расследований librarian-агентов,
> охватывающих датасеты HH.ru, альтернативные источники, исторические архивы и NLP-корпуса.

## Краткое резюме

**Основной источник:** HH.ru API — доминирующая российская платформа вакансий (80%+ рынка). Требуется живой сбор.

**Ключевой вывод:** Крупных, чистых, готовых датасетов HH.ru по естественно-научным специальностям не существует. Необходим самостоятельный сбор через API. Для доступа к HH.ru API обязательна OAuth2-авторизация (https://dev.hh.ru).

## HH.ru (HeadHunter) API

### Детали API

| Атрибут | Значение |
|-----------|-------|
| **Базовый URL** | `https://api.hh.ru` |
| **Эндпоинт поиска** | `GET /vacancies` |
| **Эндпоинт деталей** | `GET /vacancies/{id}` |
| **Авторизация** | OAuth2 обязательна (403 на анонимных запросах с 2025+) |
| **Регистрация** | https://dev.hh.ru |
| **Ограничение скорости** | ~2–3 запроса/сек (недокументировано, эмпирически) |
| **Максимум результатов на поиск** | 2,000 (20 страниц × 100 per_page) |
| **Обязательные заголовки** | `User-Agent` с идентифицирующим именем |

### Ключевые параметры API

```
GET /vacancies?
  text=физик              # Поисковый запрос (нечёткое совпадение)
  &area=113               # ID региона: 113=Россия, 1=Москва, 2=СПб
  &professional_role=100  # Фильтр по проф. роли (100=Наука/Образование)
  &per_page=100           # Результатов на страницу (макс 100)
  &page=0                 # Номер страницы (с нуля)
  &only_with_salary=true  # Только вакансии с зарплатой
```

### Professional Role ID

| ID | Категория |
|----|----------|
| 96 | Производство, сервисное обслуживание |
| 100 | Наука, образование |
| 101 | Информационные технологии |
| 102 | Медицина, фармацевтика |
| 103 | Строительство, недвижимость |
| 104 | Административный персонал |
| 112 | Рабочий персонал |
| 116 | Добыча сырья |

### Стратегия ограничения скорости

```python
# 2 запроса/сек = минимальный интервал 500 мс
# Экспоненциальная задержка при ответах 429
# Параллельная загрузка деталей (asyncio, I/O-bound)
# Последовательный поиск по специальностям (соблюдение глобального лимита)
```

## Реализация в hh-competency

Раздел описывает текущее состояние кодовой базы `src/hh_competency/`, реализующей полный пайплайн сбора, хранения и обработки данных вакансий HH.ru.

### HTTP-клиент HH.ru API

Клиент находится в `src/hh_competency/api/client.py` и построен на `httpx` с асинхронным I/O:

- **RateLimiter** — ограничение 2 запроса/сек (минимальный интервал 500 мс между запросами), глобальный для всех операций клиента
- **RetryHandler** — экспоненциальная задержка при ответах 429 (Too Many Requests), автоматический повтор с jitter-ом
- **OAuth2** — обязательная авторизация через токен доступа, полученный при регистрации приложения на https://dev.hh.ru
- **User-Agent** — идентифицирующий заголовок вида `hh-competency/X.Y.Z (research project; contact@example.com)`

### Пайплайн сбора данных

Пайплайн реализует четырёхэтапный процесс:

```
Поиск (search) → Пагинация (paginate) → Дедупликация (deduplicate) → Детали (fetch details)
```

1. **Поиск** — запрос `GET /vacancies?text=<специальность>&professional_role=100&area=113` для получения количества результатов и структуры страниц
2. **Пагинация** — последовательный обход страниц (`page=0..19`, по 100 вакансий на страницу) до исчерпания или достижения лимита HH.ru в 2,000 вакансий
3. **Дедупликация** — удаление повторяющихся вакансий по `vacancy.id`, оставшихся после пагинации (одна и та же вакансия может появиться на разных страницах)
4. **Загрузка деталей** — параллельный асинхронный запрос `GET /vacancies/{id}` для каждой уникальной вакансии с соблюдением ограничения скорости

Все этапы журналируются с указанием специальности, количества полученных/пропущенных вакансий и временных меток.

### Хранение в DuckDB

Данные сохраняются в DuckDB с использованием четырёхтабличной схемы:

| Таблица | Назначение | Ключевые поля |
|---------|-------------|---------------|
| `scrape_runs` | Журнал запусков сбора | `run_id`, `specialty`, `started_at`, `vacancies_found`, `vacancies_fetched` |
| `raw_vacancies` | Сырые JSON ответы API | `vacancy_id`, `specialty`, `scrape_run_id`, `raw_json`, `fetched_at` |
| `skill_frequencies` | Агрегированные частоты навыков | `skill_name`, `skill_name_normalized`, `specialty`, `frequency`, `scrape_run_id` |
| `specialty_profiles` | Профили компетенций по специальностям | `specialty`, `top_skills`, `skill_count`, `vacancy_count`, `updated_at` |

Извлечение полей из сырого JSON выполняется через SQL-оператор `->>` в DuckDB, например:

```sql
SELECT raw_json->>'$.name' AS title,
       raw_json->>'$.description' AS description,
       raw_json->>'$.key_skills' AS skills
FROM raw_vacancies
WHERE specialty = 'physics';
```

DuckDB выбран по следующим причинам: встроенная поддержка JSON, компактное хранение (сжатие), отсутствие отдельного сервера БД, быстрая аналитика на JSON-колонках.

### Русский NLP: обработка текста вакансий

Стек лингвистической обработки, применяемый к тексту описаний вакансий:

| Компонент | Инструмент | Функция |
|-----------|-----------|---------|
| **Токенизация** | `razdel` | Разбиение текста на предложения и слова (учитывает русскую пунктуацию, сокращения) |
| **Лемматизация** | `pymorphy3` | Приведение слов к нормальной форме (словарная форма): «требуются» → «требоваться», «знания» → «знание» |
| **NER (опционально)** | `natasha` | Выделение именованных сущностей (PER, ORG, LOC) для фильтрации |
| **Стоп-слова** | Двухуровневый фильтр | (1) Стандартные русские стоп-слова (предлоги, союзы, частицы); (2) Специфичные для вакансий стоп-слова («компания», «вакансия», «требуется», «опыт», «условия») |

Двухуровневый фильтр стоп-слов важен: стандартный список удаляет общеязыковой шум, а специализированный список очищает типовые формулировки вакансий, не несущие информации о навыках.

### Извлечение коллокаций

Для выделения составных терминов применяется поиск биграмм по паттерну:

- **ADJF + NOUN** — прилагательное + существительное (например: «квантовая физика», «математическое моделирование», «рентгеновская дифракция»)

Кроме грамматического паттерна, используется словарь из **40 известных русскоязычных STEM-словосочетаний** (захардкожен в `src/hh_competency/nlp/collocations.py`). Этот словарь захватывает устоявшиеся научно-технические термины, которые могут не попадать под паттерн ADJF+NOUN, например: «физика твёрдого тела», «анализ данных», «машинное обучение».

### Используемые внешние датасеты

При разработке NLP-пайплайна использовался `russian-oracle/vacancy-section-classifier-ru` (Hugging Face, 18K размеченных предложений) как эталонный датасет для:

- Валидации эвристик выделения разделов вакансий
- Оценки качества извлечения секции требований/навыков
- Калибровки двухуровневого фильтра стоп-слов

Этот датасет загружается при первом запуске NLP-пайплайна и кешируется локально.

### Векторные представления (navec)

Для вычисления семантической близости навыков используется `navec_news` (250K слов, 300-мерные векторы). Выбор `navec_news` обоснован:

- Обучен на формальных русских новостных текстах — тот же регистр, что и текст вакансий
- `navec_hudlit` (художественная литература) даёт систематически худшие результаты на технической лексике: термины вроде «дифракция» или «спектроскопия» имеют менее релевантные соседи в пространстве художественных текстов
- `navec_twitter` (социальные сети) непригоден из-за разговорного стиля

Векторная модель загружается один раз при инициализации и используется для кластеризации навыков по семантической близости (косинусное расстояние) и нормализации синонимичных терминов.

## CLI: команды сбора

Сбор данных запускается через интерфейс командной строки. Основные команды:

```bash
# Сбор вакансий по одной специальности
hh-competency scrape specialty physics

# Сбор по всем 13 специальностям последовательно
hh-competency scrape all

# Сбор с ограничением количества вакансий
hh-competency scrape specialty chemistry --max-vacancies 500

# Просмотр статуса последнего сбора
hh-competency status

# Просмотр статуса по конкретной специальности
hh-competency status --specialty biology
```

Перед первым запуском необходимо зарегистрировать приложение на https://dev.hh.ru, получить `client_id` и `client_secret`, и указать их в переменных окружения:

```bash
export HH_CLIENT_ID="your_client_id"
export HH_CLIENT_SECRET="your_client_secret"
```

## Качество данных: известные проблемы

### Известные проблемы данных HH.ru

1. **Несогласованные названия должностей:** «Научный сотрудник», «Researcher», «R&D Scientist», «Физик-исследователь» — одна роль, разные названия
2. **Дубликаты вакансий:** Одна и та же вакансия перепубликуется в разных городах/у разных работодателей
3. **Отсутствие данных о зарплате:** ~40% вакансий не содержат информации о зарплате
4. **Шаблонные описания:** Некоторые работодатели используют типовые описания без реальных требований к навыкам
5. **Смешанный язык:** Вакансии содержат и русские, и английские термины («Python разработчик», «MATLAB modeling»)
6. **Нечёткий поиск:** Поиск HH.ru намеренно нечёткий — возвращает слабо релевантные результаты

### Стратегия смягчения

1. **Дедупликация:** Хеш-дедупликация по ID вакансии + порог схожести содержания
2. **Обработка зарплат:** Раздельный анализ вакансий с указанием зарплаты и без
3. **Обнаружение шаблонов:** NLP-эвристика для типовых описаний (низкое лексическое разнообразие)
4. **Обработка языка:** Единообразная лемматизация и русских, и английских терминов
5. **Точность поиска:** Поиск API для полноты (recall), NLP-фильтрация по ключевым словам для точности (precision)
